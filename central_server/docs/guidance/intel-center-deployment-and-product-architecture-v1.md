# 0. 结论先行

## 0.1 最终部署结论
本项目应采用：

# **中央服务器 + 员工电脑 Local Agent 的混合式架构**

不是：
- 每个员工电脑各跑一套完整系统；
- 也不是所有浏览器采集都放在云服务器。

## 0.2 架构理由
该方案同时满足：

1. **统一产品与共享数据**
   - 主管看全局；
   - 员工看自己的账号和任务；
   - 内容全局去重；
   - 关键词、规则、对标账号组统一管理。

2. **真实账号与推荐流需求**
   - 员工自己的账号登录态保留在本机；
   - 推荐流依赖账号画像；
   - 登录、验证、养号均在员工侧更合理。

3. **多员工、多账号**
   - 一台员工电脑托管多个账号；
   - 中心统一派发任务；
   - Agent 本地排队执行，避免账号同时高频操作。

4. **可演进**
   - 后续可接抖音；
   - 可增加中央 Worker 执行部分低风险任务；
   - 可引入代理策略、行为策略、任务调度策略。

# 1. 架构决议记录（ADR）

## ADR-001：系统采用单一中央服务
### 决议
全公司/全项目只部署一套中央系统：
- Web 前端；
- API 服务；
- 主数据库；
- 任务调度；
- 内容共享池；
- 规则与配置中心。

### 不采用
“每个员工电脑各跑一套完整系统”。

### 原因
若各自独立部署：
- 主管无法统一看板；
- 多员工内容无法去重；
- 对标账号组、关键词规则难以统一；
- 后续素材库、任务分发、客资提醒无法协同。

---

## ADR-002：浏览器采集执行落在 Local Agent
### 决议
所有依赖真实账号会话的引擎，Phase A 默认由员工电脑上的 Local Agent 执行：

- 推荐页情报引擎；
- 对标账号监控引擎；
- 关键词搜索聚合引擎。

### 原因
- 真实账号会话在本地；
- 浏览器 Profile 归属员工；
- 登录/验证码/人工验证需要员工处理；
- 推荐流依赖账号自身行为历史；
- 当前 XHS 链路已基于本地浏览器/CDP 跑通。

---

## ADR-003：登录态不集中托管到云端
### 决议
中央服务器只保存会话元信息，不保存浏览器 Profile 原文，不集中管理敏感登录 Cookie 明文。

### 中央保存
- `account_id`
- `agent_id`
- `profile_ref`
- `session_status`
- `last_validated_at`
- `session_capabilities`

### 本地保存
- Chrome Profile；
- 登录 Cookie；
- 浏览器本地存储；
- Agent 本地会话缓存。

### 原因
- 减少集中泄露面；
- 避免云端统一托管大量账号态；
- 贴合员工自己登录、自己养号的业务场景。

---

## ADR-004：Agent 主动拉任务，不由中心主动侵入员工机器
### 决议
Agent 主动：
- 注册；
- 心跳；
- Claim Job；
- 上报 Progress；
- 上报 Complete/Fail。

### 原因
- 穿透 NAT 简单；
- 部署友好；
- 安全边界清晰；
- 已与当前 Job/Agent 协议一致。

---

## ADR-005：IP/代理策略与行为节奏策略独立成架构层
### 决议
不将代理/IP 和动作节奏散落在 Connector 内，而是拆成：

1. `Network Egress Policy`
2. `Behavior Risk Policy`

### 原因
- 这是执行策略，不是平台业务逻辑；
- 后续需按账号、任务、平台灵活配置；
- 便于统一审计与灰度。

# 8. 反爬/风控策略的架构位置

# 8.1 总原则
风控策略不属于页面层，也不属于平台 Connector 的零散实现。  
它应由：

```text
中心调度策略
+
本地执行策略
+
网络出口策略
```

三层共同完成。

---

# 8.2 中心调度策略（Risk Scheduler）

## 配置维度
- 每账号任务预算；
- 每账号每日最大采样量；
- 每账号最小任务间隔；
- 每 Agent 最大并发数；
- 每类任务执行窗口；
- 异常后冷却时间；
- 单日失败阈值；
- 是否允许自动恢复。

## 示例策略
```text
账号 A：
- 推荐页任务每天最多 12 次
- 每次最多 50 条
- 任务间隔不少于 30 分钟
- 连续 3 次验证异常后暂停
```

---

# 8.3 本地行为策略（Behavior Runtime）

## 行为项
- 滚动间隔；
- 点击间隔；
- 页面停留；
- 刷新间隔；
- 每轮最大动作数；
- 异常页面立即停；
- 评论读取节奏；
- 对标主页翻页节奏。

## 不应硬编码在平台 Connector
这些要抽象为：
```python
BehaviorProfile
```

例如：
```text
conservative
balanced
aggressive
```

# 8.4 网络出口策略（Network Egress Manager）

## 设计原则
对于账号登录态任务，**默认不是随机轮换 IP**。  
默认应保持：
- 稳定出口；
- 稳定账号环境；
- 稳定本地设备。

## 策略枚举
```text
DIRECT_LOCAL
FIXED_PROXY_PER_ACCOUNT
POOL_PROXY_FOR_ELIGIBLE_TASK
```

## 推荐默认
| 任务 | 默认出口 |
|---|---|
| 推荐页 | DIRECT_LOCAL 或 FIXED_PROXY_PER_ACCOUNT |
| 对标监控 | DIRECT_LOCAL 或 FIXED_PROXY_PER_ACCOUNT |
| 搜索聚合 | DIRECT_LOCAL，后续可扩 POOL_PROXY_FOR_ELIGIBLE_TASK |
| 非账号态公开抓取 | 后续可用 POOL_PROXY_FOR_ELIGIBLE_TASK |

# 8.5 代理池放在哪里
### 中央服务器负责
- 代理资源登记；
- 代理健康状态；
- 策略分配；
- 哪个账号绑定哪个固定代理；
- 哪些任务可使用池代理。

### Local Agent 负责
- 按策略实际使用代理；
- 任务执行时应用；
- 上报代理可用性与失败。

# 14. 关键不可变原则

1. 不回到“每员工一套独立系统”。
2. 不把账号登录态集中托管到中央服务器。
3. 不把 IP/代理逻辑写死在 Connector。
4. 不把动作节奏逻辑写死在平台平台解析函数。
5. 不让 Agent 变成无状态脚本，它是长期运行执行端。
6. 不让上层产品绕开统一情报池。
7. 三类引擎必须汇入统一内容资产模型。
8. 对标账号组必须能映射业务账号类型。
9. 中央服务器要负责规则、调度、共享、提醒。
10. Local Agent 要负责真实账号执行与本地会话。

# 15. 最终架构一句话

# **中央系统负责“组织、规则、调度、共享与业务流转”，Local Agent 负责“真实账号会话、浏览器执行与本地采集”。**

在这个边界下，情报中心上层产品才能既满足团队协作，又保留真实账号采集能力，并且后续扩抖音、代理策略、行为策略时不需要推倒重来。
