## 1. 产品定位

帮运营**在一台电脑上同时管理多个账号、减负**：在员工本地把全网（小红书、抖音）的**对标账号**和**优质图文/视频**采集回来，**存进本地、在本地浏览筛选**；运营把看中的内容**收藏进素材库（上报中央持久化）**并打标签。

**架构基调——本地优先**：
- **日常采集/浏览全在本地**：员工电脑跑浏览器采集，存本地库，员工用自己的浏览器访问本地端口查看。不中转、不浪费带宽、不重复拉取。
- **中央只做联机协调 + 精华素材库**：账号池、Local Agent 生命周期、对标/关键词配置同步、以及员工"加素材库"时上报的精华内容。

**本阶段不做 AI**——选题打分、AI 总结、AI 推荐理由等仅在界面/数据上占位，不实现。

## 2. 目标与价值分层

| 层级 | 内容 | 本阶段 |
|---|---|---|
| **L1 首要** | 多账号减负：快速找到优秀同行账号、优质图文/视频内容 | 做 |
| **L1** | 识别**获客转化力**内容（评论获客信号） | 做 |
| **L2** | 素材库 + 标签：把好内容上报中央沉淀（供后续 AI 训练 / 新员工培训"什么是好的" / 主管全局产出） | 做（排在本地采集与展示之后） |
| L3 远期 | 一个页面统一回复多账号的私信 / 评论 | 不做，架构预留 |
| 贯穿 | 去重、反检测、本地性能 | 随开发推进，不单列 |

## 3. 用户与使用场景

- **用户**：一线运营（同时管理多个账号）。本阶段以**员工自用**为主，主管全局视图为远期（见 §8）。
- **核心场景**：
  1. 运营在本地搜一个关键词，看到该领域的优质笔记/视频列表，点开看详情；
  2. 运营盯住若干优秀同行（对标博主），系统**本地定时监控**，有更新在本地界面红点提醒；
  3. 运营按点赞、话题、获客力等筛选，找到值得借鉴的内容；
  4. 运营把看中的内容**收藏进素材库（上报中央）**，打标签归类。
- **数据可见性**：每个员工只看自己采集的数据（本地库天然隔离）。素材库也按员工隔离（同一素材不同员工的标签可能不同），但中央记录每条素材的归属员工、加入时间、标签，为将来主管全局产出预留。

## 4. 数据流（核心逻辑）

```
日常：本地采集 → 本地存储（去重）→ 本地展示（运营筛选/查看）
沉淀：运营"加素材库" → 上报中央（精华内容持久化 + 缓存封面 + 记录 owner/时间/标签）
联机：账号池、Agent 注册心跳、对标/关键词配置同步 走中央 API
```

主干：**先在本地把数据采回来存好去重、再本地展示，最后才是把精华上报中央素材库**。日常采集与浏览不经过中央。

## 5. 功能需求

### 5.1 采集（数据来源，本地执行）

- 平台：**先小红书，抖音兼容**（两边采集已基本就绪）。
- 数据来源：搜索、对标博主、推荐流、长尾词；内容详情；评论。
- 要补的能力：
  - **博主维度（Creator）画像**：粉丝数、获赞收藏总数、作品数、认证类型、简介、IP 属地——判断对标账号是否值得跟；
  - 内容的"关联话题""平台标签""视频时长""广告/合作标识""IP 属地"字段；
  - 评论获客信号；抖音的详情/评论/对标对齐。
- **搜索是异步任务**：运营提交关键词后，Agent 采集需几秒到几十秒，界面要有"采集中 → 完成"状态。

### 5.2 存储（本地库，去重）

- **本地全量存储**：员工采到的内容存在本地，量小（单人几万条元数据），本地数据库完全够用。
- **一条内容只存一份**：按 `平台 + 平台内容ID` 唯一去重；指标变化只保留最新值（不存历史快照），记录"数据更新时间"。
- **来源关系单独记录**：一条内容可由"对标博主X""搜索关键词Y""推荐流"多个来源发现，来源记录"监控时间"（来源级首次采到时间）。
- **媒体只存 URL**：不下载图片/视频，浏览器直连平台 CDN 加载。**仅在"加素材库"时缓存封面小图**，避免素材长期图裂。
- 目的：本地快、省带宽、省空间，避免数据爆炸。

### 5.3 展示（本地 Web，给运营看）

- 员工用自己的浏览器访问本地端口查看（本地 Web UI）。三个核心界面字段需求如下。

**A. 对标博主 - 笔记列表（含博主画像）**
博主画像（昵称、头像、粉丝数、获赞收藏、作品数、认证、IP 属地）+ 笔记列表（序号、封面、标题、点赞、关联话题、笔记类型、发布时间、平台笔记标签、监控时间、数据更新时间）。

**B. 笔记详情**
博主名称、封面、标题、正文内容、点赞、收藏、评论、分享、关联话题、全部图片、发布时间。

**C. 搜索页 - 笔记列表**
关键词、笔记列表（封面、标题、作者、点赞、关联话题、笔记类型、发布时间、数据更新时间）。AI 总结、AI 推荐理由占位不做。

> A 与 C 是同一内容模型的不同来源视图；B 是单条内容的展开。

### 5.4 对标更新提醒 & 推荐流定时刷新（本地）

- **对标更新提醒**：本地定时监控对标博主，与本地库 diff 出新内容，在本地界面红点/计数提醒（自用版无需中央推送）。
- **推荐流定时刷新**：本地定时器周期重采推荐流，保持内容时效（平台会推新）。
- 实现口径：本地"采集任务"带定时配置，本地调度执行；对标"新内容数"= 本次采到时间晚于该对标"上次查看时间"的内容数。

### 5.5 素材库 + 标签（联机中央）

- **素材库 = 把精华上报中央持久化**：运营从本地"收藏"内容进素材库时，把这一条内容快照上报中央（含缓存封面），作为公司资产沉淀。
- **标签按员工各自存**：同一素材不同员工可打不同标签。中央记录每条素材的归属员工、加入时间、标签集合。
- **隔离**：素材库本阶段不跨员工可见；中央保留 owner/时间/标签信息，供 §8 主管全局产出与后续 AI。

### 5.6 获客信号（识别优质内容，手动触发）

- 评论里出现"求推荐 / 怎么买 / 多少钱 / 链接"等词，说明该内容有**获客转化力**。
- 能力：运营在本地**手动触发**对某条内容"查获客信号"→ 采评论 → 本地匹配获客关键词 → 给内容标"获客力"（命中数 + 命中评论）。
- **不全量采评论**（量大且风控高），按需触发。小红书、抖音都要支持。

### 5.7 长尾词联想

- 采集平台搜索联想词，存本地，作为运营搜索建议；后续可"一键深挖"前 N 个长尾词（排在本地闭环之后）。

## 6. 数据模型（概念层）

只描述概念实体与归属层，不涉及表结构细节（详见数据库设计文档）。

| 实体 | 含义 | 归属 |
|---|---|---|
| 博主（Creator） | 平台博主画像，去重一份 | 本地 |
| 内容（Content） | 一条笔记/视频（含详情），去重一份（平台+内容ID） | 本地 |
| 来源（Source） | 内容怎么被发现：对标/搜索/推荐 + 监控时间 | 本地 |
| 评论命中（CommentHit） | 命中获客词的评论 | 本地 |
| 长尾词（Suggestion） | 搜索联想词 | 本地 |
| 采集任务（CollectTask） | 搜索/对标/推荐意图 + 定时 + 上次查看 | 本地 |
| 员工（Employee） | 系统使用者，数据归属 | 中央 |
| Local Agent | 员工电脑采集程序实例 | 中央 |
| 平台账号（PlatformAccount） | 账号池 + 限速配置（Profile/会话留本地） | 中央 |
| 配置（TaskConfig） | 对标/关键词配置同步备份 | 中央 |
| 素材（Material） | 上报的精华内容快照，去重一份 | 中央 |
| 收藏（Collection） | 员工对素材的收藏：owner + 时间 + 标签 | 中央 |

## 7. 明确不做（防止方向偏移）

- 不做 AI（打分/总结/推荐理由仅占位）；
- 不做多账号统一私信/评论回复（仅架构预留）；
- 不扩采集平台广度（只小红书 + 抖音）；
- 不做指标历史快照（只存最新值）；
- 不做跨员工数据/素材共享浏览（本阶段员工自用）；
- 不做主管全局产出界面（中央留好数据，界面远期）；
- 不过度设计、不为不确定的未来需求提前抽象。

## 8. 远期预留（不实现，仅保证不返工）

- **主管全局产出**：中央素材库记录每条素材的 owner/时间/标签，将来直接聚合出"团队产出 / 各员工素材质量分布"，无需改采集端。
- **AI**：中央素材 + 标签是后续 AI 训练与"什么是好内容"判断的原料；数据模型预留可被 AI 消费。
- **多账号私信/评论回复**：保持"账号—会话—Agent"边界清晰，回复类动作与只读采集解耦，后续作为独立能力接入。
- **跨员工协作/去重**：将来若需要，中央可在素材层做跨员工聚合，不影响本地优先主干。
