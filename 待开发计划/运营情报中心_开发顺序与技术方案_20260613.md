# 运营情报中心 · 开发顺序与技术方案

> 版本：v1（2026-06-13，本地优先架构）
> 定位：回答"用什么技术、怎么改、按什么顺序做"。配套《产品需求文档 v2》《数据库设计 v1》。
> 替代：原《运营情报中心_开发顺序规划_20260613.md》（已废，那份在上一轮被删且未成功重写）。

## 0. 一句话方向

架构定为 **本地优先（Local-First）**：采集 + 存储 + 展示在员工本地，中央退化为"联机协调 + 精华素材库"。这同时满足了"省带宽、不重复拉取、本地快"和"数据是公司资产可交接"两个诉求——前者靠本地，后者靠中央只存账号/配置/精华。

---

## 1. 技术架构

```
员工电脑（Local Agent，一人一套）
  采集：Playwright/CDP 真实浏览器（XHS 全、抖音补齐）
  存储：本地 SQLite（情报流水，单机单写，量小）
  展示：本地 Web（FastAPI + 静态前端，localhost:端口）
  调度：本地定时器（推荐流刷新 / 对标监控）
  反检测：本地节奏控制器
        │ 仅在 注册/心跳/账号/配置同步/加素材库 时联机
        ▼
中央服务器（轻量）
  FastAPI + PostgreSQL 17（Docker Compose 部署）
  账号池 / Agent 生命周期 / 配置同步 / 精华素材库 / 软件分发
```

### 1.1 数据库选型

| 端 | 选型 | 理由 |
|---|---|---|
| 本地 | **SQLite** | 单机单写、量小（单人几万条元数据），零运维、单文件易备份。本地优先下不存在并发写。 |
| 中央 | **PostgreSQL 17** | 一步到位、上公网可移植（pgvector 向量 / pg_trgm 检索都在库内）；JSONB 适配半结构化；虽本阶段负载低，但避免将来换库返工。 |

### 1.2 部署

- 中央：`docker-compose`（FastAPI + PostgreSQL + 数据卷），Alembic 迁移，环境变量切换配置，`pg_dump` + WAL 归档备份。
- 本地：Local Agent 打包成可分发安装包，配置中央地址后注册接入；本地 Web 随 Agent 启动。

## 2. ⚠️ 架构迁移影响 + 复用定位（合并后版本）

**原则**：中央**只存筛选打标签的素材库精华**，不存全平台全量流水；全量采集流水在**本地**采、存、看。

**合并后中央已模块化**（同事 934956c）：`shared_contracts`(协议) + domain 包 `accounts/content/jobs/reference_library/operations/rules/organization`。这让"复用"地基已就绪——很多功能不用再造轮子。

| 模块 | 合并后现状 | 本阶段目标 | 工作量 |
|---|---|---|---|
| 采集 probe / 归一化 / `shared_contracts` | 本地 + 共享协议 | 直接复用 | 小 |
| 全量内容入库（ingestion） | 上报中央 | 改写**本地 SQLite** | 中 |
| 全量内容查询/列表/搜索 | 中央 `content_query`/`content_repository` | 在本地 Web 重做（参考其逻辑，本地不能 import 中央）| 大 |
| 全量浏览前端 | 中央 Web | **本地 Web** | 中 |
| 账号池/Agent | 中央 `accounts` | **复用保留** | 小 |
| 对标登记/定时 | 中央 `creator_monitors`/`benchmark_groups` | **复用**为对标配置同步 | 小 |
| 素材库（owner/时间/标签）| 中央 **`reference_library_items` 已建好** | **直接复用**，不造 material/collection | 小 |
| 获客/初筛 | 中央 `lead_detection`/`content_screening` 脚手架 | 逻辑复用到本地获客 | 小 |
| 媒体 media_service | 中央代理/落盘 | 仅素材库精华缓存封面 | 小 |

**好处**：采集层 + 共享契约 + 中央素材库/账号/对标全部复用；现在没上线、无生产数据，是改造最佳窗口。
**代价**：**全量内容的"存储+浏览"要在本地建一套**（本地不能 import 中央 storage，按红线只能本地自建轻量 SQLite 存储 + 本地 Web），这是本次最大工作量。

## 3. 数据库改造重估（回应你对 SQLite 性能的担心）

你担心的"SQLite 撑不住"，前提是**中央扛 20 Agent 并发写 + 20 员工并发读**（见《性能与反检测改进计划》§1-2）。**本地优先把这个前提推翻了**：

- 采集写的是**各自本地 SQLite**，单机单写，无并发锁库；
- 中央只接收**低频"加素材库"上报**（一天几条/几十条），并发几乎为零。

因此原性能文档里的结论要重估：

| 原项 | 原定级 | 本地优先下重估 |
|---|---|---|
| P1 SQLite WAL 调优 | P0 | **仍做**（本地库随手开 WAL）|
| P2 迁移 PostgreSQL | P0（救并发）| **降级**：中央上 PG 是为"可移植/上公网/不返工"，非救并发 |
| P5 job SKIP LOCKED | P1 | **基本不需要**（本地无 job 争抢）|
| P3 列表 keyset 分页 | P1 | 降级（本地单人数据量小）|
| P4 搜索走索引 | P1 | 本地用 SQLite FTS5 即可 |
| E1 采集行为人性化 | P0 | **不变，仍 P0**（反检测是本地，跟架构无关）|
| E2 风险策略执行化 | P1 | **不变，仍重要**（账号冷却/每日预算是上线底线）|

**结论**：本地优先后，"数据库性能"从 P0 硬骨头降为可控；反检测（E1/E2）反而是真正不能省的硬约束。

## 5. 开发顺序

### E0 · 地基与架构迁移（先做）
- **E0.1** 本地库底座：SQLite + WAL，按数据库设计建本地 7 张表（Alembic 或轻量迁移）。
- **E0.2** ingestion 改写：采集结果写**本地仓库**（替换原"上报中央"目标），复用归一化契约。
- **E0.3** 本地上报可靠性：采集结果先落本地、失败重试，避免抖动丢数据。
- **E0.4** 反检测底线：账号级最低采集间隔 + 每日上限（哪怕先写保守默认值），防上线即封号。
- **E0.5** 中央复用确认：复用 `accounts`/`creator_monitors`/`reference_library_items`（素材库）；platform_accounts 补限速字段；PG + Docker Compose 起库。不新建 material/collection。

### S0 · 数据模型定稿
- 建 Creator 实体 + 内容补字段（话题/平台标签/视频时长/广告/IP 属地/获客）；两级时间戳（内容级 first/last_seen、来源级监控时间）。

### S1 · 本地"采→存→看"第一闭环
- 本地 Web 展示：搜索页列表 + 详情页（读本地库）；搜索异步 + "采集中"状态。

### S2 · 对标本地监控 + 提醒
- collect_task(creator_monitor) 本地定时执行 → diff → 红点；博主画像采集。

### S3 · 获客信号（手动触发）
- 单条内容"查获客信号"→ 采评论 → 本地匹配 → comment_hit + 标记。

### S4 · 推荐流定时刷新
- collect_task(recommend) 本地定时器；抖音 /jingxuan 已验证，接入本地闭环。

### S5 · 素材库联机（复用 reference_library）
- "加素材库"→ 上报中央：upsert `content_identity`/`content_snapshots`（仅该精华，缓存封面）+ insert `reference_library_items`（owner/时间/标签）；对标配置同步到 `creator_monitors`。

### S6 · 抖音对齐
- 抖音 detail/comment probe 接入；creator 采集补齐，对齐统一内容模型。

### 后续（按需）
- 反检测策略深化（冷却/退避/健康度映射）、主管全局产出、AI、回复——挂载式接入。

---

## 6. 明确不做（本阶段）
- 不做中央全量内容存储/查询/展示（改本地）；
- 不做中央 job 高并发机制（本地无争抢）；
- 不做 ES / 分布式 / 消息队列 / 媒体全量下载 / 指标历史快照 / 跨员工共享；
- 不做 AI / 主管界面 / 回复（留锚点，按需挂载）。

---

## 7. 架构红线（沿用，本地优先下补充）
1. 不把 central / local 揉回一个包；
2. Local Agent 不 import 中央 DB/storage/services，只 HTTP JSON 联机（注册/心跳/账号/配置/素材上报）；
3. 中央不 import `local_agent_runtime`；
4. 不上传 Cookie 原文、Profile 留本机；
5. `references/MediaCrawler` 仅参考不作运行依赖；
6. 改采集逻辑必须跑 smoke audit，禁用过期 URL 验收；
7. 动作能力（回复）与只读采集解耦。
