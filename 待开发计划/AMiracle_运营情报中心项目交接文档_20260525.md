## 1. 一句话说明项目

AMiracle 当前不是单纯的爬虫脚本，也不是完整成品运营后台，而是一个正在成型的 **运营情报中心**：通过“中央服务器 + 员工电脑 Local Agent”的架构，让多个员工、多个真实平台账号在各自电脑上保留登录态，由中央统一分发任务、采集小红书等平台内容、去重入库、补详情/评论，并在前端情报中心里供运营人员筛选、分配、沉淀为对标作品库/素材库/线索库。

当前重点不是自动发布，也不是全自动运营账号；当前阶段重点是把 **采集引擎、账号登录态、任务中心、情报池、运行可观测性** 做稳。

## 3. 已确定的总体架构决策

### 3.1 采用“中央服务器 + 员工电脑 Local Agent”

这是当前项目最核心的架构决策。

原因：

1. 主管需要看全局数据、统一任务、统一规则、统一情报池。
2. 员工账号的真实登录态必须保留在员工电脑本地，尤其是小红书推荐流依赖账号画像和本地登录会话。
3. 多员工、多账号需要中央统一派发任务、本地排队执行，避免所有账号集中在云端带来的登录态、安全和风控问题。
4. 后续可以继续扩展抖音、视频采集、封面分析、AI 筛选，但不能破坏这个分层。

### 3.2 登录态不集中托管到中央

中央只保存账号、Agent、Session 元信息，例如：

- `account_id`
- `agent_id`
- `profile_ref`
- `session_status`
- `last_validated_at`
- `session_capabilities`

本地保存：

- Chrome Profile
- Cookie
- 浏览器 Local Storage
- 登录状态缓存

硬约束：**不保存或上传 Cookie 原文**。

### 3.3 Agent 主动拉任务

Local Agent 通过 HTTP 主动：

1. register
2. heartbeat
3. claim login session
4. claim jobs
5. start/progress/complete/fail job
6. ingestion 上报

中央不主动侵入员工机器，这样部署、NAT、安全边界都更清晰。

## 9. 当前主链路：从任务到情报入库

### 9.1 推荐流任务链路

当前推荐页主链路：

```text
前端创建 recommendation_feed_task 模板
  ↓
POST /api/task-templates/{id}/run
  ↓
TaskMaterializationService.run_template
  ↓
创建 TaskRun
  ↓
创建 feed_collect Job
  ↓
Local Agent claim job
  ↓
XhsHomeFeedProbe.collect
  ↓
POST /api/ingestion/feed-candidates
  ↓
写入 ContentIdentity + ContentDiscoveryEvent
  ↓
为新内容创建 detail_fetch Job
  ↓
feed_collect Job complete
  ↓
Local Agent 后续 claim detail_fetch
  ↓
XhsDetailProbe.fetch_detail
  ↓
POST /api/ingestion/content-detail
  ↓
写 ContentSnapshot，并按策略创建 comment_fetch
  ↓
Local Agent claim comment_fetch
  ↓
XhsCommentProbe.fetch_comments_result
  ↓
POST /api/ingestion/comments
  ↓
写 CommentSnapshot
```

这条链路是当前 MVP 最重要链路之一。

### 9.2 对标账号监控链路

```text
创建 BenchmarkGroup / BenchmarkGroupMember
  ↓
创建 creator_monitor_task 模板
  ↓
运行模板
  ↓
TaskRun + 多个 creator_monitor Job
  ↓
Local Agent 执行 XhsCreatorConnector.fetch_latest
  ↓
POST /api/ingestion/creator-monitor-items
  ↓
去重入库
  ↓
为新增内容创建 detail_fetch
```

### 9.3 关键词搜索链路

```text
创建 keyword_search_task 模板
  ↓
运行模板
  ↓
TaskRun + search_collect Job
  ↓
Local Agent 执行 XhsSearchProbe.collect
  ↓
POST /api/ingestion/feed-candidates
  ↓
去重入库 + 详情补采
```

### 9.4 搜索联想词链路

```text
POST /api/xhs/search-suggestions/tasks
  ↓
xhs_search_suggest Job
  ↓
Local Agent 执行 XhsSearchSuggestProbe
  ↓
POST /api/ingestion/xhs-search-suggestions
  ↓
中央保存建议词
```

## 10. 当前任务系统的关键概念

| 概念 | 说明 |
|---|---|
| `TaskTemplate` | 任务模板，例如推荐流任务、对标账号监控任务、关键词搜索任务 |
| `TaskSchedule` | 任务调度，目前支持手动和 interval 类能力，后续可完善每日时间窗 |
| `TaskRun` | 一次任务运行批次，用来聚合多个 Job 的状态和摘要 |
| `Job` | Local Agent 真正领取和执行的最小任务 |
| `JobEvent` | Job 状态事件 |
| `FetchLease` | 详情/评论/创作者补采 lease，避免重复补采 |
| `checkpoint_json` | 任务断点和执行进度 |
| `result_summary_json` | 任务结果摘要，供运行中心和任务中心展示 |
| `error_summary_json` | 错误摘要 |

Job 状态：

```text
pending → claimed → running → success / partial_success / failed / cancelled
```

TaskRun 状态：

```text
materialized → queued → running → success / partial_success / failed
```

## 11. 当前情报数据组织方式

### 11.1 内容身份层

`ContentIdentity` 是内容唯一身份层，解决全局去重问题。

关键字段语义：

- `platform`
- `platform_content_id`
- `canonical_url`
- `content_type`
- `source_surface`
- `metadata_json`
- `data_status`
- `candidate_bucket`

### 11.2 发现事件层

`ContentDiscoveryEvent` 记录内容是从哪里被发现的，例如：

- 推荐流
- 搜索
- 对标账号监控
- 手动导入

这样同一个内容被多个员工/多个账号刷到，也可以复用内容身份，而不是重复获取。

### 11.3 详情快照层

`ContentSnapshot` 存详情数据，例如：

- 标题
- 正文
- 作者
- 封面
- 图片 URL
- 视频 URL
- 点赞/评论/收藏/分享
- 发布时间
- raw payload

### 11.4 评论快照层

`CommentSnapshot` 存评论数据，用于后续线索识别、用户痛点分析、评论区高频问题提取。

### 11.5 运营工作流层

围绕内容进行人工运营处理：

- `ContentWorkflowState`
- `ContentAssignment`
- `ContentOperatorNote`
- 状态：`pending_review` / `assigned` / `selected` / `discarded` / `archived`

### 11.6 参考库层

`ReferenceLibraryItem` 用于把内容沉淀成运营资产：

- 对标作品
- 线索案例
- 视觉素材

这块是后续“从采集到运营复用”的关键承接点。

## 12. 当前规则与策略中心

当前已经有以下策略/规则模型：

| 模型 | 作用 |
|---|---|
| `KeywordRuleSet` / `KeywordRule` | 关键词规则集，用于初筛、业务关键词、求推词、线索词等 |
| `BusinessAccountTypeRuleSet` | 将业务账号类型和规则集绑定 |
| `BehaviorProfile` | 行为策略，后续控制滚动、停留、刷新节奏 |
| `NetworkEgressProfile` | 网络出口策略，后续控制直连/代理/账号出口 |
| `RiskPolicy` | 风险预算策略，后续控制频次、冷却、失败阈值 |

当前策略模型已经在任务模板字段里预留，但执行层还没有完全做成强策略引擎。后续要继续把“行为节奏、网络出口、风险预算”从 connector 里抽出来，不要散落在采集代码里。

任务落地时会校验执行账号必须是 `intelligence_collector`。

### 13.3 平台账号健康状态

`health_status` 用来表示账号健康度：

```text
healthy
warning
cooling_down
blocked
disabled
```

这块后续要和失败重试、手动验证、风险预算、行为策略打通。

## 15. 当前仍然不算完成的地方

### 15.1 前端体验还需要重做

当前前端已经有页面和功能入口，但整体 UI/信息架构还不是最终形态。之前已经明确过：界面需要更像“高密度运营/金融风控制台”，而不是松散卡片堆叠。

后续前端方向：

- 页面要更紧凑
- 表格/筛选/状态信息优先
- 少用大面积圆角卡片和空白
- 运行状态要一眼能看懂：等待、执行中、成功、失败、部分成功、补采中
- 情报中心要支持快速筛选、批量处理、分配、沉淀参考库
- 任务中心要明确“模板、运行记录、Job 明细”的层级关系

### 15.2 行为策略 / 网络出口 / 风险预算还没有完全执行化

模型和字段有了，但不是所有 connector 都已经真正消费这些策略。

后续要做：

- `BehaviorProfile` 控制滚动次数、停留时间、刷新间隔、单账号任务间隔
- `NetworkEgressProfile` 控制直连/代理/账号固定出口
- `RiskPolicy` 控制任务频率、失败次数、冷却、风控错误处理
- 把策略执行和采集 connector 解耦

### 15.3 小红书能力还缺第二层、第三层

当前已做的是第一层只读采集。

未完成：

- 二级评论
- 当前账号已发布笔记
- 当前账号点赞/收藏内容
- 搜索用户
- 创作者平台作品列表
- 私信/通知读取
- 发布/评论/点赞/收藏/关注/上传等动作能力

当前不建议马上做动作能力，应该先把只读采集、任务、情报池、运营工作流稳定。

### 15.4 抖音还没有正式接入

代码和枚举已经预留 `douyin`，但当前正式 runtime 能力主要是 XHS。

后续抖音不要直接复制 XHS，而是按照同一套 Capability Contract 和 Local Agent Runtime 模式接入：

- douyin homefeed video
- douyin homefeed image/text
- detail
- comment
- creator latest
- normalize 到统一内容模型

### 15.5 AI 分析还没有成为主链路

当前项目应该先保证数据采集和工作流。AI 后续再接：

- 内容质量评分
- 对标账号质量评估
- 封面/图片/视频结构分析
- 评论区痛点/线索识别
- 选题聚类
- 素材库标签自动生成
- 给运营生成“为什么值得看”的摘要

不要在采集主链路还不稳时把 AI 自动决策做太深。

## 19. 当前必须遵守的架构红线

接手后不要破坏以下红线：

1. **不要把 central_server 和 local_agent 再揉回一个包。**
2. **Local Agent 不得 import 中央 DB/storage/services。**
3. **中央服务不得 import `local_agent_runtime`。**
4. **Local Agent 不得直接写中央数据库，只能 HTTP JSON 上报。**
5. **不要上传 Cookie 原文，不要把 Chrome Profile 放进代码包。**
6. **不要把 `references/MediaCrawler` 当正式运行依赖。**
7. **不要绕过 TaskTemplate → TaskRun → Job 的任务链路。**
8. **不要让动作能力混入当前只读采集 MVP。**
9. **不要把行为策略和网络策略散落进各个 connector。**
10. **不要用过期 URL 验收 detail/comment，应使用当前 session 新鲜抓到的 URL 或 smoke 模式。**

## 20. 当前已知风险和注意事项

### 20.1 测试环境风险

我在当前沙盒里尝试运行中央 pytest，但沙盒没有安装依赖，报错：

```text
ModuleNotFoundError: No module named 'sqlalchemy'
```

这不是代码包本身的业务错误，而是当前审阅环境缺少依赖。接手同事应在 `D:\AMiracle\.venv` 安装 requirements 后再跑测试。

### 20.2 SQLite 与未来生产部署

当前默认 SQLite，适合本地演示和开发。后续如果进入多员工真实使用，应考虑：

- PostgreSQL
- 对象存储 / 本地 artifact 存储规范
- 日志归档
- 数据备份
- 账号和任务审计

### 20.3 小红书平台变化风险

小红书页面结构、签名、xsec、评论接口、验证码/风控都可能变化。当前的审计机制必须保留，后续每次改采集逻辑都要有 smoke audit。

### 20.4 多账号运行节奏风险

一个员工电脑可能托管多个账号，但不能并发高频刷。需要 Local Agent 本地排队、账号冷却、任务频率限制。

### 20.5 前端产品复杂度风险

不要把所有功能都堆到一页。前端应该围绕三个主对象组织：

1. 情报内容
2. 任务运行
3. 账号/Agent 状态

## 22. 当前项目交接结论

当前项目已经过了“脚本探索阶段”，进入了“产品化骨架 + 真实采集能力打通”的阶段。
