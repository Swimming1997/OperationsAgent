# 运营情报中心 · 数据库设计

> 版本：v1（2026-06-13，本地优先架构）
> 定位：数据库表结构的事实来源，是建表与迁移的依据。配套《产品需求文档 v2》《开发顺序与技术方案》。
> 目标：高质量、可扩展、可移植、高性能、不过度设计。

## 0. 设计原则

1. **对齐三件事**：采集能产出什么、产品要展示什么、数据怎么流转——不设计采集填不满或展示用不上的字段。
2. **本地优先双库**：员工本地存全量情报流水（SQLite），中央只存联机协调数据 + 精华素材库（PostgreSQL）。
3. **能合并就合并，能字段就别拆表**：减少 join。据此把详情并入内容、会话/Profile 留本地、对标更新用字段+查询替代通知表。
4. **去重一份**：内容/博主按平台业务键全局唯一（本地库内）。
5. **指标只存最新**：不存历史快照，记数据更新时间。
6. **媒体只存 URL**：不下载；仅"加素材库"时缓存封面。
7. **挂载式可扩展**：AI / 精细化标签 / 回复后续一律"加表挂在稳定主键"，不改核心表。
8. **全在关系库内**：向量用 pgvector、检索用 pg_trgm（中央）/ 本地用 SQLite FTS5，不引入外部组件。

## 1. 通用约定

- 本地库主键：`id INTEGER PRIMARY KEY`（SQLite 自增）；中央库主键：`id BIGINT GENERATED ALWAYS AS IDENTITY`（紧凑、join 快）。
- 业务唯一键：另设唯一约束（如 `平台+平台内容ID`），用于去重与 upsert。
- 时间统一 `TIMESTAMP`（中央用 `TIMESTAMPTZ`）；半结构化用 `JSON`（中央 `JSONB` + 按需 GIN）；大文本 `TEXT`。
- `↗` 表示外键。

## 2. 库与表总览

### 2.1 本地库（每个员工电脑一份，SQLite）—— 情报流水 7 张

| 层 | 表 | 作用 |
|---|---|---|
| 情报 | `creator` | 博主画像（去重一份）|
| 情报 | `content` | 内容（含详情，去重一份）|
| 情报 | `content_source` | 来源（对标/搜索/推荐 + 监控时间）|
| 情报 | `comment_hit` | 获客信号命中评论 |
| 搜索 | `search_suggestion` | 长尾词联想 |
| 调度 | `collect_task` | 本地采集意图（搜索/对标/推荐，含定时、上次查看）|
| 调度 | `collect_run` | 一次执行记录（重试/审计）|

### 2.2 中央库（PostgreSQL）—— 联机协调 + 精华素材库 6 张

| 层 | 表 | 作用 |
|---|---|---|
| 用户 | `employee` | 系统使用者，数据归属与登录 |
| 采集端 | `local_agent` | 员工电脑采集程序实例（注册/心跳/版本）|
| 采集端 | `platform_account` | 账号池 + 限速配置（Profile/会话留本地）|
| 配置 | `task_config` | 对标/关键词配置同步备份（换机/交接可拿回）|
| 素材库 | `material` | 上报的精华内容快照（去重一份，缓存封面）|
| 素材库 | `collection` | 员工收藏：owner + 时间 + 标签（主管全局产出入口）|

**扩展预留（不建）**：AI `material_ai_analysis` / `material_embedding`、精细化标签 `tag`/`collection_tag`、回复 `dm_*`/`comment_reply`、素材库文件夹 `collection_folder`。

## 3. 数据流转

```
本地：Agent 采集 → 本地 upsert
  → creator（画像去重，更新最新）
  → content（按平台+内容ID去重，更新最新指标；详情按需填）
  → content_source（本次来源+监控时间）
  → (获客) comment_hit + 回写 content.acquisition_*
  → (长尾) search_suggestion
本地展示：员工浏览器 → 本地 Web 读 content/creator/content_source → 列表/详情
对标提醒：collect_task.last_viewed_at vs content_source.first_seen_at → 新内容数

中央：员工"加素材库" → 上报一条
  → material（按平台+内容ID去重，缓存封面）
  → collection（owner=该员工 + 加入时间 + 标签）
联机：local_agent 注册/心跳；platform_account 账号池；task_config 配置同步
```

## 4. 本地库表定义（SQLite）

**4.1 `creator`**（博主画像，去重一份）
id / platform / platform_user_id / nickname / avatar_url / fans_count / total_liked_collected / works_count / verify_type / signature / ip_location / first_seen_at / last_seen_at
约束 `(platform, platform_user_id)` 唯一。

**4.2 `content`**（含详情，去重一份）
id / platform / platform_content_id / creator_id↗ / content_type(图文/视频) / title / cover_url / published_at / **topics**(JSON 关联话题) / **platform_tags**(JSON 平台标签) / video_duration / is_ad / ip_location / like_count / comment_count / collect_count / share_count / **body_text**(TEXT 详情正文) / **image_urls**(JSON 全部图片) / detail_fetched_at / **acquisition_hit_count**(获客命中数) / acquisition_checked_at / first_seen_at / last_seen_at(数据更新时间)
约束 `(platform, platform_content_id)` 唯一；索引 creator_id、published_at；标题检索用 FTS5 虚表。
说明：详情并入本表，列表查询只 select 需要的列、不读大字段、免 join。

**4.3 `content_source`**（来源 + 监控时间）
id / content_id↗ / source_type(creator/search/recommend) / source_ref(博主ID或关键词) / first_seen_at(对标=监控时间) / last_seen_at
约束 `(content_id, source_type, source_ref)` 唯一；索引 `(source_type, source_ref, last_seen_at)`。
说明：本地库天然只有本员工数据，无需 owner 字段；对标列表 = 本表(source_type=creator, source_ref=博主) join content。

**4.4 `comment_hit`**（获客命中评论）
id / content_id↗ / comment_text / comment_author / like_count / matched_keyword / published_at / fetched_at
说明：只存命中获客词的评论，命中数回写 content.acquisition_hit_count。

**4.5 `search_suggestion`**（长尾词联想）
id / platform / core_keyword / suggested_keyword / rank / fetched_at；索引 `(platform, core_keyword)`。

**4.6 `collect_task`**（本地采集意图 + 定时）
id / task_type(search/creator_monitor/recommend) / target(关键词或博主ID) / params(JSON) / schedule_seconds(空=一次性) / last_run_at / **last_viewed_at**(算对标新内容) / status / created_at

**4.7 `collect_run`**（执行记录）
id / task_id↗ / status / started_at / finished_at / attempts / item_count / error_summary(JSON)
说明：本地单机执行，无并发争抢，不需要 SKIP LOCKED；本表仅作重试与审计。

## 5. 中央库表定义（PostgreSQL）

**5.1 `employee`**
id / name / username(唯一) / password_hash / role(预留) / status / created_at

**5.2 `local_agent`**
id / employee_id↗ / device_name / fingerprint(唯一) / version / status / last_heartbeat_at / created_at

**5.3 `platform_account`**（账号池 + 限速；Profile/会话留本地，不存 Cookie 原文）
id / employee_id↗ / platform / account_name / platform_user_id / health_status / bound_agent_id↗ / daily_quota / min_interval_seconds / created_at
约束 `(platform, platform_user_id)` 唯一。

**5.4 `task_config`**（对标/关键词配置同步，换机可拿回）
id / employee_id↗ / config_type(creator_monitor/search) / target / params(JSONB) / schedule_seconds / updated_at
约束 `(employee_id, config_type, target)` 唯一。
说明：本地 collect_task 的"配置部分"同步副本；执行与流水仍在本地。

**5.5 `material`**（上报的精华内容快照，去重一份）
id / platform / platform_content_id / creator_nickname / content_type / title / cover_url / **cached_cover_path**(缓存封面) / published_at / topics(JSONB) / platform_tags(JSONB) / like_count / comment_count / collect_count / share_count / body_text(TEXT) / image_urls(JSONB) / created_at
约束 `(platform, platform_content_id)` 唯一；同一素材多员工收藏只存一份内容，省空间、利于 AI 原料与去重。

**5.6 `collection`**（员工收藏：owner + 时间 + 标签）
id / employee_id↗ / material_id↗ / tags(JSONB 字符串数组) / note / collected_at
约束 `(employee_id, material_id)` 唯一；索引 `(employee_id, collected_at DESC)`、tags GIN。
说明：标签按员工各存（同素材不同员工标签不同）。**主管全局产出 = 按 employee_id 聚合 collection join material**，无需改采集端。

## 6. 关系总览

```
中央：employee 1─* local_agent
      employee 1─* platform_account
      employee 1─* task_config
      employee 1─* collection *─1 material
本地：creator 1─* content 1─* content_source
                       content 1─* comment_hit
      collect_task 1─* collect_run
      search_suggestion（独立小表）
跨库：本地 content 被"加素材库"时 → 上报生成中央 material + collection
```

## 7. 扩展预留蓝图（不建，只留锚点）

- **主管全局产出**（锚点 collection）：直接对 `collection join material` 按 employee 聚合查询/物化视图，零改表。
- **AI**（锚点 material.id）：`material_ai_analysis`(scores, ai_summary, ai_reason, ai_tags) + `material_embedding`(vector, pgvector)。
- **精细化标签**（锚点 collection）：从 collection.tags(JSONB) 升级为规范 `tag`(employee_id↗, name, category, parent_id↗) + `collection_tag`，仅当需要分类/层级时再迁移。
- **素材库文件夹**（锚点 collection）：`collection_folder` + collection.folder_id。
- **账号回复**（锚点 platform_account.id）：`dm_conversation` + `dm_message` + `comment_reply`。

## 8. 设计取舍

1. **本地优先双库**：情报流水留本地（量小、可重采、读取快、省带宽），中央只存账号/配置/精华（公司资产、怕丢、要交接、可聚合）。
2. **本地无并发问题**：单机单写，SQLite 足够；不需要 SKIP LOCKED、连接池等中央高并发机制（详见技术方案对"数据库改造"的重估）。
3. **详情并入 content、会话/Profile 留本地、对标更新用字段+查询替代通知表**——减表减 join。
4. **内容/素材去重一份**：本地按内容ID去重；中央素材按内容ID去重一份，多员工收藏靠 collection 区分 owner 与标签——同素材不重复存内容，又支持每人不同标签。
5. **话题/平台标签用 JSON**（采集来）；运营标签先用 collection.tags(JSON)，需要分类层级时再升级独立表。
6. **限速字段就地放 platform_account**，不建策略表。
7. **可移植**：中央 PG 一步到位（向量/检索都在 PG 内），本地 SQLite 单文件易分发备份；上公网无需换库。
