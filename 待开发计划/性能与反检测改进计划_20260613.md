# AMiracle 性能与反检测改进计划

> 归档说明：本文是 2026-06-13 性能、反检测与采集能力推进记录，仅作为背景材料保留；当前 P2 开发事实来源为 `central_server/docs/guidance/p2-development-plan.md`。若本文与 P2 开发落地计划冲突，以 P2 开发落地计划为准。
>
> 生成时间：2026-06-13
> 适用范围：`central_server`（中央服务/网页/DB）+ `local_agent`（采集引擎）
> 原定位：在历史交接文档基础上，针对两大核心痛点——**爬取引擎反检测/稳定性** 与 **中央服务在 20+ 并发下的性能** ——给出按优先级排序的改造记录；当前仅作背景材料。
> 阅读对象：继续改这个项目的同学。每一项都带"现状证据 + 改法 + 验收标准"，可直接照着做。

---

## 0. 一句话结论

项目骨架健康（中央/本地拆分清晰、DB 索引覆盖完整、路由是同步 `def` 不会阻塞事件循环），但两大核心点都停留在"能跑"而非"能扛"：

1. **爬取引擎没有任何反检测策略落地**——滚动节奏完全机械、固定，`BehaviorProfile`/`RiskPolicy` 三张策略表存在却一行都没被消费。这是"被平台误判恶意爬取"的最大风险源。
2. **中央服务在目标并发（≥20 员工 + ≥20 Local Agent 同时在线）下，SQLite 单写入者必然成为瓶颈**，导致写锁竞争、读卡顿。这是网页性能问题最可能的真凶。

---

## 1. 真实运行场景与并发模型（本次确认）

- 部署形态：**所有员工登录同一个中央服务器**，在网页上操作/查询自己需要的情报；
- 数据来源：员工自己的 Local Agent 执行采集，或从中央"公共资源池"直接取数据；
- 并发规模：**至少 20 个员工同时在线 + 各自的 Local Agent 同时运行**，设计上必须覆盖这种并发可能引发的卡顿/锁库/重复领取等 bug。

由此推导出中央服务同时承受两类高并发负载：

| 负载来源 | 行为 | 频率（按 20 个估算） | 性质 |
|---|---|---|---|
| 员工浏览器 | 情报列表、筛选、搜索、翻页、详情 | 持续、突发 | 读为主 |
| Local Agent | register / heartbeat / claim jobs / ingestion 上报 | heartbeat 30s、poll 5s、ingestion 突发批量 | 写为主 |

**结论**：读写高并发会同时发生。SQLite 是库级单写入者，20 个 Agent 的 ingestion 写 + job 领取（也是写）会被串行化，并阻塞前端读。这是当前架构在目标并发下的硬瓶颈。

## 2. 现状评估（带证据）

### 2.1 爬取引擎

**问题 E1（P0）：采集行为完全机械，无反检测。**

`local_agent/local_agent_runtime/connectors/xhs/homefeed_probe.py`：固定滚动 `1800px` + 固定停顿 `1200ms`，无随机抖动、无鼠标轨迹、无随机停留：

```text
await page.mouse.wheel(0, 1800)
await page.wait_for_timeout(self.scroll_pause_ms)  # 固定 1200ms
```

全局检索确认 `local_agent_runtime` 内**没有任何用于行为节奏的随机化**（唯一的 `random` 在 `api_client.py` 仅用于生成 `search_id`）。真人不可能每次滚动距离/间隔完全一致——这是典型机器人指纹。

**问题 E2（P1）：策略模型存在但执行层零消费。**

`BehaviorProfile` / `RiskPolicy` / `NetworkEgressProfile` 在中央有表、在任务模板里预留了字段，但 `runtime.py` 与所有 connector **完全没有读取/执行**。导致：

- 无账号级冷却（一个账号刚跑完可立即被派下一个 job）；
- 无单账号每日采集频次预算（多账号同机无节制连刷 = 风控高危场景）；
- `max_jobs_per_claim=1` + `poll 5s`，job 之间无人性化间隔。

**问题 E3（P2）：homefeed/search 走 DOM 抓取，脆弱。**

homefeed 靠 `CARD_EXTRACTION_SCRIPT` 解析 DOM class（probe 自己在 `fragile_points` 承认 class names 不是稳定 API），detail/comment 才走签名只读 API（`api_client.py`）。小红书一改版 DOM 路径整片失效。

### 2.2 中央服务性能

**问题 P1（P0）：SQLite 零调优，并发必锁。**

`central_server/intelligence_engine/db/session.py` 仅 `check_same_thread=False`，**无 WAL、无 `busy_timeout`、无 `synchronous` 调优**。20 Agent 并发写会串行 + 触发 `database is locked`。

**问题 P2（P0/架构）：SQLite 撑不住 20 并发，需迁移 PostgreSQL。**

WAL 只能缓解"读写并存"，写仍然全局串行。≥20 Agent 持续 ingestion + job 领取，SQLite 单写入者是硬上限。交接文档已注明"JSON 类型兼容 PostgreSQL JSONB、未来可切 PG"——现在就是要切的时候。

**问题 P3（P1）：情报列表查询偏重。**

`content_repository.py::list_intelligence_contents`：窗口函数子查询 + 4 个 outer join + `group_by` + `order by max(discovered_at)` + `offset` 分页 + 独立全表 `count`。20 用户并发翻页、深 offset 时变慢。

**问题 P4（P1）：搜索是 JSON 全表扫描。**

`content_query.py`：`func.lower(ContentIdentity.metadata_json.cast(Text)).contains(lowered)` 把整个 JSON cast 成文本做 `LIKE %kw%`，无法走索引，必然全表扫描。

**问题 P5（P1）：job 领取在高并发下会争抢/重复领取。**

20 Agent 每 5s `claim_jobs`，SQLite 无 `SELECT ... FOR UPDATE SKIP LOCKED`，靠应用层加锁很脆弱，易超时或重复领取。PostgreSQL 的 `SKIP LOCKED` 是正解。

### 2.3 架构判断

- 路由全部是同步 `def`，由 FastAPI 线程池执行（默认约 40 线程），**不会阻塞事件循环**——这点设计正确，不用大改。
- 真实瓶颈在 **DB 层（SQLite）** 和 **热点查询/搜索**，不在 Web 框架层。
- 多员工多租户架构（用户/角色/组织/权限）确认是真实需求，**保留**，不做瘦身。

## 3. 问题优先级总表

| 编号 | 问题 | 优先级 | 痛点归属 | 预估成本 |
|---|---|---|---|---|
| P1 | SQLite 无 WAL/busy_timeout 调优 | **P0** | 中央性能 | 极低（1 文件） |
| E1 | 采集行为机械、无随机化 | **P0** | 反检测 | 低 |
| P2 | 迁移 PostgreSQL（支撑 20+ 并发） | **P0** | 中央性能 | 中 |
| P5 | job 领取并发争抢（SKIP LOCKED） | P1 | 中央性能 | 中（依赖 P2） |
| E2 | 行为/风险策略执行化（冷却/预算） | P1 | 反检测 | 中 |
| P3 | 情报列表查询（keyset 分页/缓存） | P1 | 中央性能 | 中 |
| P4 | 搜索改索引字段（GIN/trgm） | P1 | 中央性能 | 中（依赖 P2） |
| E3 | homefeed/search 优先签名 API | P2 | 引擎稳定性 | 高 |
| 公共池缓存、Agent 轮询调优、前端虚拟化 | P2 | 中央性能 | 中 |

## 4. 分阶段计划

### 里程碑 0：止血（P0，目标 1-2 天，立刻见效）

不改架构，先把最低成本、最高回报的两件事做掉。

- **任务 0.1｜SQLite 性能加固**
  - 文件：`central_server/intelligence_engine/db/session.py`
  - 改法：通过 SQLAlchemy `event.listen(engine, "connect")` 对每个连接执行：
    - `PRAGMA journal_mode=WAL;`
    - `PRAGMA busy_timeout=5000;`
    - `PRAGMA synchronous=NORMAL;`
    - `PRAGMA foreign_keys=ON;`
  - 仅对 `sqlite` URL 生效，PG 时跳过。
  - 验收：开 1 个前端持续翻列表 + 跑脚本并发 ingestion，不再出现 `database is locked`；列表 p95 明显下降。

- **任务 0.2｜采集行为人性化（最关键的反检测第一道防线）**
  - 文件：`homefeed_probe.py`、`search_probe.py`，并抽一个公共 `pacing.py`。
  - 改法：
    - 滚动距离改随机区间（如 900~2000px）；
    - 停顿改随机区间（如 800~2500ms），偶发更长"阅读停留"；
    - 偶发小幅回滚（模拟回看）；
    - 每个 job 执行前后加随机间隔。
  - 注意：随机用于"节奏"，不改变采集结果正确性；保留现有 perf 计时口径。
  - 验收：连续两次 homefeed run 的 scroll 间隔/距离序列不再相同；smoke audit 仍 pass。

### 里程碑 A：支撑 20+ 并发的 DB 底座（P0/P1，目标 3-5 天）

这是覆盖"20 员工同时用导致卡顿/锁库"这一核心诉求的根本解。

- **任务 A.1｜引入 PostgreSQL 作为生产 DB**
  - 保持 SQLite 为本地开发/测试默认，通过 `DATABASE_URL` 切换。
  - 配置连接池：`pool_size`、`max_overflow`、`pool_pre_ping=True`、`pool_recycle`。
  - 校验 Alembic 全部迁移在 PG 上可跑；JSON → JSONB；`server_default`、时间类型对齐。
  - 提供 `docker-compose`（或本机 PG）一键起库 + 迁移脚本。
  - 验收：模拟 20 并发读 + 20 并发 ingestion，无锁库、p95 在目标内。

- **任务 A.2｜job 领取改 `FOR UPDATE SKIP LOCKED`（PG 路径）**
  - 文件：`storage/repositories/job_repository.py` 的 claim 逻辑。
  - PG 下用 `with_for_update(skip_locked=True)` 原子领取，杜绝重复领取与锁等待；SQLite 保留旧逻辑兼容开发。
  - 验收：20 Agent 并发 claim，无重复领取、无领取超时。

- **任务 A.3｜并发压测脚本 + 基线**
  - 新增脚本模拟 N 个员工读 + N 个 Agent 写，记录 p50/p95/错误率，作为后续回归基线。

### 里程碑 B：热点查询与搜索优化（P1，目标 3-4 天，依赖 A）

- **任务 B.1｜情报列表 keyset 分页**
  - 用 `(discovered_at, content_id)` 游标替代深 offset；`count` 改为近似/缓存或前端取消精确总数。
- **任务 B.2｜搜索走索引字段**
  - 放弃 JSON 全文 cast；PG 上对 title/author/body 建 `pg_trgm` GIN 索引，或对 `metadata_json` 建 JSONB GIN；中文场景评估 trigram。
- **任务 B.3｜公共资源池热点读缓存**
  - 对高频、低变化的公共池列表加短 TTL 缓存（进程内或 Redis），降低重复重查。
- 验收：列表/搜索 p95 在 20 并发下达标；搜索不再全表扫描（EXPLAIN 验证走索引）。

### 里程碑 C：策略执行层（P1，目标 4-5 天）

把交接文档里"模型有、执行无"的策略真正落地，从 connector 解耦。

- **任务 C.1｜Local Agent 节奏控制器**
  - 新增轻量 `PacingController`，消费 `BehaviorProfile`（滚动/停留/刷新节奏）与 `RiskPolicy`（频次、冷却、失败退避）。
- **任务 C.2｜账号级冷却 + 每日采集预算**
  - 账号刚跑完进入冷却窗口；单账号每日采集量到顶后中央不再派单（在 claim/materialization 层校验）。
- **任务 C.3｜平台错误码 → 账号 `health_status` 映射**
  - 风控/验证类错误自动把账号置 `cooling_down`/`warning`，联动重试与人工验证。
- 验收：可配置不同 profile 跑出不同节奏；触发风控错误后账号自动降级冷却。

### 里程碑 D：引擎稳定性（P2，按需）

- **任务 D.1｜homefeed/search 优先签名 API，DOM 作 fallback**（对齐 `references/MediaCrawler` 的 `client.py` 接口路径，仅参考不直接依赖）。
- **任务 D.2｜失败分类、stale running job 自动回收、审计报告一键导出。**

### 里程碑 E：前端与 Agent 轮询（P2，按需）

- 列表虚拟化、避免重复刷新风暴、筛选防抖；
- Agent `claim_jobs` 评估长轮询/退避，降低 20 Agent × 5s 的空转压力；
- heartbeat 间隔与在线判定窗口对齐。

## 5. 风险与回滚

- **PG 迁移风险**：先在测试库跑全量 Alembic + pytest，再灰度。保留 SQLite 开发默认，靠 `DATABASE_URL` 切换，可随时回退。
- **反检测随机化风险**：随机只作用于"节奏"，不得影响采集数据正确性；每次改采集逻辑必须跑 smoke audit（红线第 10 条）。
- **查询重构风险**：keyset 分页与现有前端分页契约需同步调整，分接口灰度。

---

## 6. 必须遵守的架构红线（沿用交接文档第 19 节）

1. 不把 central / local 揉回一个包；
2. Local Agent 不 import 中央 DB/storage/services，只 HTTP JSON 上报；
3. 中央不 import `local_agent_runtime`；
4. 不上传 Cookie 原文、不把 Profile 放进代码包；
5. 不把 `references/MediaCrawler` 当正式运行依赖；
6. 不绕过 TaskTemplate → TaskRun → Job 链路；
7. 不让动作能力混入只读采集 MVP；
8. 策略不散落进各 connector，统一走节奏控制器；
9. 改采集逻辑必须跑 smoke audit，禁用过期 URL 验收。

## 7. 方向决策（2026-06-13 与负责人对齐后更新）

经讨论，**当前重心调整为"引擎优先"**，先把 Local Agent 拉数据的能力和反检测做到极致，中央 20 并发性能（PG 迁移）方向已认可、排在引擎之后。关键决策：

1. **引擎优先**：先把采集引擎和反检测做扎实，再回头做中央性能。
2. **小红书与抖音共用一套反检测策略**，采用分层设计：
   - **平台无关内核（共用）**：人类行为节奏（随机滚动/停留/抖动/回看）、会话生命周期、风险策略（账号冷却、每日预算、失败退避）、错误→账号健康度映射、审计。反检测本质是"模拟人"，不分平台。
   - **平台适配层（各做各的）**：选择器、API 签名（XHS `X-S/X-T`；抖音 `a_bogus/X-Bogus`）、字段归一化、各能力 probe。
3. **起步次序**：先搭共享内核并在 XHS 上验证 → 再做抖音适配（避免反检测逻辑复制两份）。
4. **抖音采集路线**：优先真实浏览器 + DOM/拦截响应（更像真人、反检测更强、与现有 XHS 一致），签名 API 作为后续可选增强。

### 数据流结论（图片/详情是否要"本地→中央→本地"）

合理且必要：
- 详情/文本数据上中央是公共资源池的根本价值——20 人共享一份，**减少对平台的重复请求 = 直接降低风控概率**。
- 图片/封面"重新托管"不是浪费：XHS/抖音图片 CDN 有防盗链 + 过期，`media_service.py` 已实现 `proxy_ok`（能直连不落盘）/`stored`（落盘重托管）/`unavailable` 三态。
- 待优化（写入计划）：① 按需补采（只对过初筛/被点开的内容拉详情+图）；② 列表用缩略图、详情才加载大图。

### 调整后的推进次序

1. **引擎里程碑 1｜共享内核**：`PacingController`（行为人性化）+ 会话/能力契约抽象，重构 XHS 接入。
2. **引擎里程碑 2｜抖音适配层**：homefeed/search/detail/comment/creator + 归一化到统一内容模型。
3. **引擎里程碑 3｜风险策略执行化**：账号冷却、每日采集预算、错误退避（共享层消费 `BehaviorProfile`/`RiskPolicy`）。
4. **零成本随手做**：SQLite WAL 加固（任务 0.1）。
5. **中央 20 并发性能（里程碑 A/B）**：引擎稳定后启动 PG 迁移等。

> 每个里程碑结束后跑：中央 `pytest`、Local Agent `pytest`、前端 `npm test`、一次 XHS smoke audit，作为回归门槛。
