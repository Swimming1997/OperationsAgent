# 运营情报中心 V1 开发计划

> 生成时间：2026-05-26  
> 依据：`central_server/docs/guidance/运营情报中心产品说明与需求文档.docx`、当前代码结构、项目交接文档、XHS 引擎待开发计划，以及本轮沟通结论。  
> 核心原则：领域模型先行，执行层抽象先行；AI 大模型能力先占位，当前优先提升运营处理效率。

---

## 1. 当前判断

当前项目底层架构方向是正确的：

- `central_server` 负责产品、数据、任务、账号、权限、前端和运行中心。
- `local_agent` 负责员工电脑本地浏览器、Chrome Profile、账号登录态、小红书采集和 HTTP 上报。
- 已经具备 `TaskTemplate -> TaskRun -> Job -> Local Agent -> ingestion -> 情报池` 的主链路。
- 小红书只读采集能力已有基础，包括推荐流、搜索、详情、评论、创作者主页和搜索建议。

但从最新 PRD 看，项目还需要从“采集系统”升级成“运营情报与内容生产系统”。后续重点不是先做复杂 AI，而是先补齐：

- 情报中心筛选与批量处理；
- 对标作品库；
- 获客库 / 非获客库分类；
- 我的选中 / AI 选中；
- 作品评级；
- 底图库；
- 运营规则库；
- 仿写 / 仿画工作流占位；
- 账号分发与客资提醒。

---

## 2. 开发总原则

### 2.1 不推倒当前架构

当前中央服务与 Local Agent 的拆分是正确的。后续开发应继续遵守：

- 中央不直接操作员工 Chrome / Profile。
- Local Agent 不直接访问中央数据库。
- Cookie、Local Storage、Chrome Profile 不上传中央。
- 采集结果通过 HTTP JSON ingestion 上报。
- 不绕过 TaskTemplate / TaskRun / Job 主链路。

### 2.2 领域模型先于页面

不要直接按页面堆功能。应先把 PRD 的核心业务对象固化：

- 情报内容；
- 对标作品；
- 选中来源；
- 库类型；
- 作品等级；
- 关键词规则；
- 运营规则；
- 底图资产；
- 仿写项目；
- 仿画项目；
- 分发任务；
- 客资线索。

### 2.3 执行层服务先于路由堆逻辑

关键业务判断要进入 service 层，而不是写在前端或 API route 里：

- 内容筛选；
- 手动选中；
- AI 选中；
- 作品评级；
- 求推词 / 线索识别；
- 底图建议入库；
- 仿写生成；
- 仿画生成；
- 分发任务状态流转。

### 2.4 AI 大模型能力先占位

现阶段 AI 能力目标是“提高运营效率”，不是追求完整自动化。

因此：

- AI 判断先用规则实现；
- 仿写先做结构化编辑器和模板草稿；
- 仿画先做项目壳和结果归档；
- 大模型调用通过 service 接口预留；
- 所有 AI 输出必须可人工编辑、人工确认、可追溯。

## 3. 目标产品闭环

V1 应形成以下闭环：

```text
采集 / 导入内容
  -> 情报中心筛选
  -> 手动选中 / 规则选中
  -> 对标作品库沉淀
  -> 底图 / 规则 / 仿写项目沉淀
  -> 文案和素材草稿
  -> 分发到账号
  -> 发布记录
  -> 客资提醒和跟进
```

当前阶段优先做到前半段：

```text
采集 / 导入内容
  -> 情报中心筛选
  -> 手动选中 / 规则选中
  -> 对标作品库沉淀
```

| 原始情报作品 | `ContentIdentity`, `ContentSnapshot`, `ContentDiscoveryEvent` | 保留现有内容身份、快照和发现事件模型 |

### 4.2 建议新增或强化模型

#### 4.2.1 对标作品库：扩展 `ReferenceLibraryItem`（非新建表）

**决策（阶段 0 必交付，不可跳过）**：在现有 `reference_library_items` / `reference_library_events` 上扩展，**禁止**与 `BenchmarkItem` 平行双库。现有 API（`/api/reference-library/items`、`/api/intelligence/contents/{id}/reference-library-items`）、前端 `IntelligencePage` 对标 tab、`ReferenceLibraryRepository` 去重逻辑（`content_id + library_type + active`）继续作为主干。

**PRD 概念与现有字段映射**：

| PRD 概念 | 落库方式 |
|---|---|
| 库类型：获客 / 非获客 / 待分类 | 扩展 `library_type` 枚举：`lead` / `non_lead` / `uncategorized`（与现有 `benchmark_work` 等做迁移映射，见阶段 0） |
| 选中来源：我的选中 / AI 选中 | 新增 `selection_sources_json`（`manual` / `ai` 可多值）；`metadata_json.selection_locked_by_manual` 标记人工锁定 |
| 作品等级 | 扩展 `rating`：`poor` / `medium` / `good` / `watching`（与现有 S/A/B/C 做一次性迁移或并存过渡，阶段 0 定稿） |

| 平台 | 由 `content_id` -> `ContentIdentity.platform` 派生，表内不冗余 |

### 4.3 选中、评级与自动评估状态机（P0 必实现）

同一 `content_id` 在任意时刻**最多一条** `status=active` 的对标条目。

**默认方案（阶段 0 仅在有充分理由时可推翻）**：DB 部分唯一索引 `(content_id) WHERE status='active'`（PostgreSQL/SQLite 均支持），替代现有 `(content_id, library_type)` 唯一。历史若存在多条 active：保留 `selected_at` 最新的一条，其余 `archived` 并补写 `ReferenceLibraryEvent`。

| 场景 | 行为 |
|---|---|
| 手动入库 | 写入 `selection_sources` 含 `manual`；设 `selection_locked_by_manual=true`；自动评估**不得覆盖**库类型、评级、备注 |
| AI 规则入库 | 仅当无 active 条目，或存在条目且未 `selection_locked_by_manual` 时写入/更新；写入 `ai` 来源与 `ai_reason` |
| 手动改分类/评级 | 追加 `ReferenceLibraryEvent`；保持 manual 锁 |
| 规则重评 | API `POST .../re-evaluate`；跳过 `selection_locked_by_manual` 的条目；结果写事件 |
| 移出/归档后再入库 | 新 `created` 事件；继承策略阶段 0 定稿 |

**与 `CandidateDecision` 关系**：`CandidateBucket`（`lead_candidate` / `content_candidate` / …）由 `candidate_classifier` + **可配置 `RuleProfile`**（按平台、库类型）产出；`BenchmarkSelectionService` 负责 **Bucket -> `library_type` + `rating`** 映射，不与 classifier 两套阈值硬编码并存（见阶段 2）。

### 4.4 `OperationRule` 与 `KeywordRule` 边界

- **机器可执行规则**（期刊词、求推词、阈值）：继续使用 `KeywordRuleSet` / `KeywordRule` + `RuleProfile`（新增配置表或 JSON 配置，阶段 2）。
- **运营经验条文**（标题/封面/正文/风险/人设）：进入 `OperationRule`（阶段 7 P1）；含 `version`、`enabled`、引用时**快照** `rule_snapshot_json` 写入仿写项目，避免事后改规则篡改历史草稿。

## 5. 执行层服务规划

### 5.1 Central Server 服务

#### ContentScreeningService

职责：

- 期刊关键词命中；
- 平台筛选；
- 点赞 / 评论区间筛选；
- 内容是否已入库判断；
- 情报中心筛选条件组装。

#### BenchmarkSelectionService

职责：

- 手动加入我的选中；
- AI 规则选中；
- 获客库 / 非获客库 / 待分类归类；
- 差 / 中 / 好 / 待观察评级；
- 写入选择理由；
- 记录 `ReferenceLibraryEvent`。

#### LeadDetectionService

职责：

- 从评论、标题、摘要文本中识别求推类关键词（**不含私信**；`source_type=dm` 仅枚举预留，无 ingestion）；
- 生成意向客资候选（P0 可写入 `CandidateDecision` 扩展字段或通知，不必等 `Lead` 表）；
- 输出命中关键词和理由。

#### AssetExtractionService

职责：

- 从非获客作品中建议提取底图；
- 判断图片可能类型；
- 生成底图入库建议；
- 提醒敏感信息检查。

#### OperationRuleService

职责：

- 运营规则新增、编辑、启停；
- 按平台和类型查询规则；
- 提供给仿写 / 仿画项目引用。

#### RewriteService

职责：

- 选择对标作品；
- 生成结构拆解草稿；
- 引用运营规则；
- 生成模板化文案草稿；
- 后续替换为大模型实现。

初期实现：

- 不强制接大模型；
- 可使用模板、规则和原文摘要生成草稿；
- 所有结果可人工编辑。

#### ImageVariationService

职责：

- 创建仿画项目；
- 保存提示词；
- 保存生成结果；
- 后续替换为图片模型调用。

初期实现：

- 不强制接图片模型；
- 支持外部生成结果上传或手动绑定。

#### DistributionService

职责：

- 创建分发任务；
- 维护发布状态；
- 记录发布链接和互动数据；
- 关联账号、文案、底图、负责人。

**P2 拆分**：阶段 11 先做**手动分发**（文案/底图/负责人/截止时间/状态）；发布链接与互动指标为**人工回填**子阶段；自动采集回填与线索数统计另列，不阻塞 P0。

### 5.3 Local Agent 配套（接口依赖，非 central_server 实现）

当前 Local Agent 已能执行 XHS 只读任务。**以下抽象属于 `local_agent` 计划**，本计划仅定义中央侧验收的 **Job payload / 错误码 / 运行中心展示**；central_server **不实现** Profile 路径管理与 Chrome 锁。

#### CollectorExecutor

只负责只读采集：

- feed collect
- search collect
- detail fetch
- comment fetch
- creator monitor
- search suggest

#### OperatorExecutor

后续负责对外动作：

- 评论回复；
- 评论发布；
- 点赞；
- 收藏；
- 发布作品。

V1 先预留，不进入主开发。

职责：

#### AccountLock

职责：

- 同一账号串行执行；
- 同一 Profile 串行执行；
- 操作型任务优先级和锁保护；
- stale lock 清理。

#### PlatformConnector Contract

后续新增抖音前，应固化平台 connector 输出契约：

- feed 输出；
- detail 输出；
- comment 输出；
- creator 输出；
- 错误码；
- 平台上下文；
- media artifacts。

## 6. AI 能力占位策略

### 6.1 现阶段 AI 不作为主阻塞项

当前开发目标是提高运营效率，因此 AI 功能按以下方式处理：

- AI 选中：先用规则判断实现；
- AI 判断原因：先用规则命中原因生成；
- 仿写：先做结构化编辑器和模板草稿；
- 仿画：先做项目壳、提示词和结果归档；
- 客资识别：先用关键词规则；
- 大模型调用：后续在 service 层替换实现。

### 6.2 建议预留统一生成记录

可新增统一生成记录表，或在各项目表内保留生成字段。

建议字段：

- `provider`
- `model`
- `prompt_template`
- `input_snapshot_json`
- `output_json`
- `status`
- `error_message`
- `created_by_user_id`
- `created_at`

### 6.3 人工审核优先

所有 AI 或模板生成结果必须支持：

- 人工编辑；
- 保存草稿；
- 版本追踪；
- 关联来源作品；
- 关联引用规则；
- 标记采纳 / 废弃。

## 阶段 1：P0 领域模型落库

### 目标

在 `ReferenceLibraryItem` / `ReferenceLibraryEvent` 上表达选中来源、库类型、作品评级与事件追溯。

### 任务

1. Alembic 扩展 `reference_library_items`（4.2.1 字段）。

## 7.5 P0 工程约束（API / 权限 / 批量 / 性能 / 前端）

### 7.5.1 P0 API 合同（草案，阶段 0 定稿）

在现有路由上扩展或新增；所有写操作后端校验角色（见 7.5.2）。分页默认 `page_size<=50`，最大 100。

| 能力 | 方法 | 路径（草案） | 备注 |
|---|---|---|---|
| 情报列表筛选 | GET | `/api/intelligence/contents/product` | 扩展 query：平台、关键词、点赞/评论区间、发布时间、是否已入库、surface |
| 情报详情 | GET | `/api/intelligence/contents/{content_id}/product-detail` | **保留现有路径**；可选 alias `/api/intelligence/contents/{content_id}` 一版兼容期。响应含推荐库类型、`ai_reason`、命中词 |
| 手动入库 | POST | `/api/intelligence/contents/{content_id}/reference-library-items` | 已有，扩展 body：`library_type`, `selection_sources`, `note` |
| 批量入库 | POST | `/api/reference-library/items/bulk` | 见 7.5.3 |
| 对标库列表 | GET | `/api/reference-library/items` | 三层筛选 + 排序白名单 |
| 更新条目 | PATCH | `/api/reference-library/items/{id}` | 分类、评级、标签、备注 |
| 归档/移出 | POST | `/api/reference-library/items/{id}/archive` | |
| 规则重评 | POST | `/api/reference-library/items/re-evaluate` | 单条或批量 ids |
| 事件列表 | GET | `/api/reference-library/items/{id}/events` | |

错误码：复用现有 `ErrorCode` 枚举；新增项走 PR 评审，避免重复定义。

**最小 schema（阶段 0 补齐 OpenAPI）**：列表项含 `content_id`, `platform`, `title`, `like_count`, `comment_count`, `candidate_bucket`, `in_reference_library`, `matched_keywords`, `ai_reason`；入库 body 含 `library_type`, `selection_sources`, `rating?`, `note?`；批量响应见 7.5.3；RuleProfile 读写见下表扩展。

| RuleProfile CRUD（P0） | 方法 | 路径（草案） |
|---|---|---|
| 列表 | GET | `/api/benchmark-rule-profiles` |
| 更新 | PUT | `/api/benchmark-rule-profiles/{id}` | 仅 admin/supervisor；评估结果写入 `rule_profile_id` + `rule_profile_version` + `input_snapshot_json` |

### 7.5.2 权限矩阵（后端强制）

| 能力 | admin | supervisor | operator | sales |
|---|---|---|---|---|
| 情报池只读 | Y | Y | Y | Y |
| 手动入库 / 批量入库 | Y | Y | Y | N |
| 改分类 / 评级 / 标签 / 备注 | Y | Y | Y | N |
| 归档 / 删除对标条目 | Y | Y | N | N |
| 规则重评（AI） | Y | Y | N | N |
| 配置 RuleProfile | Y | Y | N | N |
| 运营规则库 CRUD（P1） | Y | Y | N | N |
| 分发 / 客资（P2） | Y | Y | 部分 | Y（仅跟进） |

敏感操作必须写 `ReferenceLibraryEvent`；前端隐藏按钮**不能**替代鉴权。

**生产鉴权**：`X-Role` / `X-User-Roles` 请求头**仅 dev/test** 可用；生产配置 `allow_header_auth=false`（或等价项），必须 Bearer token。验收：生产配置下无 token + 伪造 `X-Role: admin` 返回 401/403（覆盖 `intelligence_engine/security/auth.py` 的 `get_optional_principal` 行为）。

### 7.5.3 批量操作规范

- 单次批量上限：**50** 条（可配置）。
- 支持 `Idempotency-Key` 请求头，24h 内重复请求返回相同结果摘要。
- 响应：`{ succeeded: [...], failed: [{ id, code, message }] }`；默认 **partial success**（成功的提交，失败的逐条返回），不用全批回滚除非 `?atomic=true`（仅 admin）。
- 每条成功写入对应 `ReferenceLibraryEvent`；并发批量以 `content_id` 行锁或 DB 唯一约束保证幂等。

### 7.5.4 前端信息架构（P0）

- **情报中心**：继续 `IntelligencePage`，增强筛选、右侧详情抽屉、批量操作栏；筛选状态 URL query 持久化。
- **对标作品库**：独立路由页（如 `BenchmarkLibraryPage`），替代当前对标 tab 的只读列表；三层 Tab：平台 -> 选中来源 -> 库类型；含空状态、无权限禁用态。
- **详情**：对标库内可展开作品详情，不必强制跳回公共池（可保留“在情报池打开”链接）。
- 验收：至少 1 条 Vitest 覆盖手动入库路径 + 对标库筛选。

### 7.5.5 查询性能（阶段 3 前完成设计）

- 列表：禁止无分页全表扫描；排序字段白名单（`selected_at`, `like_count`, `comment_count` 等派生列优先落库或物化，避免任意 JSON cast）。
- 关键词：命中词优先结构化字段；若仍用 JSON contains，阶段 3 验收在 **1 万条** 内容下 P95 列表 < 500ms。
- **基准环境**：以 **PostgreSQL 16**（docker-compose）为准；SQLite 仅开发烟测。提供 `scripts/seed_intelligence_perf.py` 生成内容/快照/发现/决策/评论/对标条目；验收附 EXPLAIN 与 P95 脚本路径。
- 索引：沿用 `idx_candidate_decisions_*`、`idx_content_snapshots_*`；新增 `reference_library_items(selected_at)`、`(library_type, status)` 等按阶段 0 EXPLAIN 结果添加。

### 7.5.6 底图存储（P1 前置设计，阶段 8 前落库）

`BackgroundAsset` 需约定：文件落 `central_server/data/assets/` 或对象存储；DB 存 `artifact_id` + 鉴权下载 URL；缩略图 job；敏感状态 `unprocessed` 时原图仅 admin 可见；删除策略与 `MEDIA_DOWNLOAD` job 对接——阶段 8 开工前输出单独设计小节，**不阻塞 P0**。

### 10.1 MVP / P0（当前冲刺，必须交付）

```text
小红书采集内容
  -> 情报中心可筛选（含性能基准）
  -> 可手动加入我的选中
  -> 可按获客 / 非获客 / 待分类入对标作品库（ReferenceLibraryItem）
  -> 系统可按 RuleProfile 自动 AI 选中
  -> 对标作品库可筛选、评级、标签、备注、事件追溯
```

**P0 非目标**：底图库页面、运营规则库页面、仿写/仿画工作流 UI、分发任务、Lead 表、私信采集、自动发布。

### 10.2 V1（P0 + P1，产品闭环前半）

在 P0 基础上增加：运营规则库、底图库管理、仿写轻量版（阶段 7-9）。

### 10.3 V1.1 / P2（后半闭环）

仿画项目壳、账号分发（手动）、发布记录人工回填、客资提醒规则版（评论来源）。

### 10.4 与第 3 节闭环的关系

第 3 节描述**产品终态闭环**；**验收以 10.1-10.3 为准**，避免把 P2 能力计入 P0 验收（原第 11 节指标中底图/仿写/仿画入口改为 P1+ 考核）。

## 11. 验收总口径

**P0 验收**不以“AI 生成质量”为核心：

1. `ReferenceLibraryItem` 扩展能否表达 PRD 对标库（无平行双库）。
2. 情报筛选效率与查询性能达标（7.5.5）。
3. 对标库可管理且事件可追溯；manual 锁与批量规范（7.5.3）生效。
4. `RuleProfile` 可解释、可配置、可重评。
5. 权限矩阵后端 enforced（7.5.2）。
6. Central / Local Agent 边界清晰（5.3）。
7. XHS 稳定性 SLO 达标（阶段 6）。

**P1+ 另验**：底图/规则/仿写/仿画的数据结构与入口（见 10.2-10.3）。

---

## 12. 结论

当前项目不需要重构大架构，应该在现有中央服务与 Local Agent 架构上继续推进。

下一步最重要的是补齐领域模型和执行层服务，让项目从“采集引擎”升级为“运营情报产品”。AI 大模型能力先做占位和可替换接口，现阶段重点服务于运营效率提升，而不是做全自动内容生产。
